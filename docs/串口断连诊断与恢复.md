# 串口断连诊断与恢复（2026-10-22）

## 现场证据与结论边界

日志来源：`D:\tools\SerialLog\data\logs\AP&IOTE联调\2026-10-22\20261022_114734_930`。

- iote1（COM16）记录了 11:48:50.513、11:51:03.103、11:51:26.073、11:51:41.436 四次故障断开。
- 后两次分别紧随 AP 在 11:51:25.379、11:51:40.198 开始发送的命令组。截图中的该组只选择 AP，不是直接向所有 iote 串口发送；不能归因为同一指令被工具错发到所有窗口。
- 断开前有 `+WIOTAPGIDLE,RECV`、`status change 1 to 2` 等设备输出。仅凭这些文字不能推断设备是否进入某种休眠状态、USB 是否复位。
- iote1 重连后帧号继续增长，不能把串口重连直接解释为固件整机重启。
- 现场只读枚举：COM16/8/9/11 使用 CH340 驱动 3.9.2024.9；AP 的 COM20 使用 FTDI 驱动 2.12.36.20。驱动类型不同是排查线索，不是驱动有缺陷的证明。

旧提示“串口驱动句柄已关闭”来自工具对 `SerialPort.IsOpen == false` 的解释，并不是 Windows 原始错误描述。已确认这个判断不够精确：System.IO.Ports 8.0 的 IsOpen 还受事件监视循环状态影响。事件监视循环退出时，底层句柄可能仍然可用。

此前修复了代码层面的误判路径和清理遗漏，但旧日志没有原生句柄状态与错误码，无法证明当时四次事件都能保留原连接。

2026-10-22 下午新证据：14:13:18.368、14:13:26.564 的 COM16 诊断均为 `eventLoopStopped=True`、`GetCommState` 返回 `win32=5`，随后打开报“找不到 COM16”。用户另用串口管理工具确认 COM 口消失。这两次属于系统端口暂时不可用，不是可继续读取的事件监视退出。设备状态输出和发送时序相关，但仍不能断言 USB、供电、CH340 驱动中的具体根因。

## 修复策略

1. 每次连接缓存唯一 BaseStream，接收和发送复用该流，不额外打开 COM 口。
2. 当托管 IsOpen 变为 false 时，只读检查运行库的事件循环状态与 SafeFileHandle，并通过 GetCommState、ClearCommError 验证原句柄可访问。
3. 仅在“明确是事件循环停止、句柄未关闭/无效、原生调用成功”时保留连接，改为 50 ms 周期读取。界面日志提示“已切换轮询接收（未断开）”。运行库字段不匹配、状态不明或原生调用失败时仍进入故障断开流程。
4. 轮询和原有事件读取共享接收锁，保留每次最多读取 256 KiB 的限制、日志半行、Ymodem 独占与失效检测。原有用户启用的静默重连策略不变。
5. 真正关闭时显式释放缓存 BaseStream，避免 SerialPort.Dispose 在 IsOpen 为 false 时跳过内部流清理。自动重连仍等待旧连接清理，不抢占未释放端口。
6. 显示、保存、协作等事件订阅者抛异常时记录诊断，不将此类异常当成串口故障关闭连接。
7. 发送失败不自动重放命令，避免已部分写入时重复执行。轮询恢复状态下修改波特率会提示先断开重连，并恢复原值显示，避免只修改托管缓存却假称硬件参数已变更。

实现依赖当前固定的 System.IO.Ports 8.0 内部字段，只读访问，不篡改或重启内部事件线程。升级该包时必须重新验证字段契约和恢复测试。

## 新增诊断日志

路径：`<当前运行工具目录>\data\diagnostics\serial-<进程ID>.log`。工程预览对应：

`D:\code\serial-log\publish-latest\data\diagnostics`

- 独立于窗口的自动保存开关。
- 记录打开/主动关闭调用来源、会话与连接代次、COM、波特率、构建标识、程序目录、事件循环状态、句柄状态、当前原生探测错误码、收发队列、收发累计字节和最近活动时间、引脚/驱动警告、异常堆栈、清理结果。
- `lastRxUtcTicks`、`lastTxUtcTicks` 是 UTC 的 .NET ticks；外层时间戳含本地时区，便于与串口日志对齐。
- 每个进程按约 2 MiB 轮转，最多保留当前文件及 `.1`、`.2`。现在按整个目录的受管理诊断文件施加 **32 MiB 总量、7 天保留期限**；写入时清理最旧文件，跨进程写入采用互斥保护。
- 只清理 `serial-数字.log`、`.log.1`、`.log.2`，不递归、不触碰工作区配置/串口采集日志或其他文件，不跟随重解析点。被锁定而无法清理时停止新增写入，不为诊断影响串口。
- 使用容量 256 条的后台写入队列，接收线程不等待磁盘；拥塞时丢弃新诊断并尽力记录丢弃计数。正常进程退出最多等待 500 ms 排空，崩溃/强制结束可能丢失队尾。`sourceTime`、`sourceThread` 是事件源时间/线程，外层时间是实际写入时间。
- 不主动保存完整命令或固件二进制；路径、会话标识和异常信息仍可能包含内部信息，外发前检查。
- 诊断写入失败不阻塞业务异常处理；目录不可写时可能没有诊断文件。

注意：`win32` 是本次原生探测的结果，不是已经退出的 .NET 事件线程当时的原始错误码。GetCommState 只查询配置；查询接收队列使用的 ClearCommError 会清除通信错误标志，返回的错误位会保留到诊断中。

## 回归与实机验收

### 首批日志延迟修复

现场四个 CH340 窗口在 14:11:17.578 出现“接收已验证”，大批日志直到 14:11:18.585 才取得解析时间戳，故不是单纯绘制延迟。已确认原路径在共享线程池同步 Read，健康补捞间隔 1 秒，并在解析之前调用诊断订阅者、在整轮收取结束后才提交日志。这些是延迟放大路径；旧日志未分段计时，不能断言每一毫秒的来源。

修复后每连接使用一个独立后台接收线程，事件只唤醒，不在线程池回调内同步 Read；启动立即检查，事件缺失时默认 50 ms 补捞。首批完整日志及时交付，不等下一次读取或持续数据达到 256 KiB。“接收已验证”和该块解析内容同批发布，连接状态通知在提交之后；本地保存/显示入队先于协作通知。继续使用原串口流、接收锁、二进制租约及日志虚拟化，不新增第二个物理读取者。

详细诊断默认关闭；排查时**关闭当前工具**，在 PowerShell 临时启动一个带开关的进程：

```powershell
$savedSerialTrace = $env:SERIALLOG_TRACE_RECEIVE
try {
    $env:SERIALLOG_TRACE_RECEIVE = '1'
    Start-Process -FilePath 'D:\code\serial-log\publish-latest\SerialLog.App.exe'
} finally {
    $env:SERIALLOG_TRACE_RECEIVE = $savedSerialTrace
}
```

开关仅在新进程启动时读取，不写工作区配置。记录底层读取耗时、收取与解析合计耗时、订阅者提交耗时、字节/行数、是否线程池线程；每连接约 5 秒限频，无命令内容。后续普通启动回到轻量模式。暂未对这套真实硬件实测修复后的延迟，不将 50 ms 补捞周期当成端到端时延保证。
