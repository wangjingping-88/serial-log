# 剪贴板复制成功却提示失败

## 现象与依据

2026-10-22，用户反馈每次复制日志都提示 `OpenClipboard 失败 (0x800401D0 / CLIPBRD_E_CANT_OPEN)`，但可正常粘贴。

工具原来在后台 STA 线程调用 WPF `Clipboard.SetText`，对其全部异常统一提示“复制失败”。WPF 8.0 源码中，该调用先执行 `OleSetClipboard`，再执行 `OleFlushClipboard` 以持久化内容；两步都可能争用剪贴板。因此，整个调用抛异常不等价于文本完全没有写入。现场现象与写入后的争用相符，但没有现场异常调用栈，不能确定具体占用程序或断言必定在 Flush 失败。

## 修复

- 文本复制改为 Win32 `CF_UNICODETEXT` 即时渲染写入，取消 OLE 延迟渲染和二次 Flush；日志与命令复制复用同一实现。
- 保留后台 STA 线程，UI 与串口采集不等待剪贴板锁。
- 创建不可见的消息窗口作为所有者。禁止以空 HWND 打开后直接清空、写入。
- 先分配并填充带零结尾的 UTF-16 内存；分配失败不清空原剪贴板。
- 打开被占用时最多尝试 20 次，间隔 50 ms；成功后只清空、写入一次，不反复改写剪贴板。
- `SetClipboardData` 返回成功后，内存所有权交给系统，不再释放；数据不依赖临时线程继续存活。失败则释放未转移的内存，关闭已打开的剪贴板并销毁窗口，保留明确失败提示。
- 不通过读取现有剪贴板文本或吞掉异常来假定成功。打开一直失败时不会清空旧内容；已经清空后若系统写入失败，无法保证恢复旧内容。

## 验证边界

自动测试覆盖短暂占用重试、持续占用失败、成功后的单次写入与所有权转移、分配/清空/写入失败清理，以及中文、多行、emoji、空文本和长文本的原生内存布局。测试不会覆盖或读取用户剪贴板。

实机仍需验证：复制日志和命令后能粘贴；关闭工具后内容仍可粘贴；剪贴板管理器运行时无误报；持续占用时仍提示失败。没有主动关闭剪贴板管理器或其他程序。
